# German Coach App — Data Model
> This document defines the core data structures for the app.
> Every feature in the product brief depends on this being right from day one.
> Agree on this before writing any backend code.

---

## Philosophy

Every progress, re-engagement, and motivation feature in this app feeds from stored history. If the data isn't captured from day one, these features cannot be built later without a painful migration.

**Rule: store more than you think you need, from the very first session.**

### Task
> Generated by AI, stored so we can reference what was given vs what was written.

```json
{
  "id": "uuid",
  "user_id": "uuid",
  "created_at": "timestamp",
  "title": "Ein freier Tag",
  "description": "Beschreibe, was du an einem freien Tag am liebsten machst.",
  "level": "B1",
  "effective_level": "B1",
  "injected_words": ["uuid_word_1"],
  "status": "completed",
  "type": "normal"
}
```

**Task types:**
```
normal          → standard daily task
re_engagement   → shorter, lower barrier (after 2+ week absence)
quiz_writing    → uses a specific word from pool (v2)
```

### Word
> The core of the library. Every word has independent counters per modality.

```json
{
  "id": "uuid",
  "user_id": "uuid",
  "german": "Entschuldigung",
  "english": "apology / excuse me",
  "article": null,
  "part_of_speech": "noun",
  "added_at": "timestamp",
  "source_submission_id": "uuid",
  "status": "active",
  "mastery": {
    "write": {
      "count": 7,
      "target": 20,
      "last_used": "timestamp"
    },
    "see": {
      "count": 4,
      "target": 20,
      "last_seen": "timestamp"
    },
    "say": {
      "count": 0,
      "target": 20,
      "last_used": null
    }
  },
  "synonyms": [],
  "archived_at": null,
  "injection_history": [
    {
      "task_id": "uuid",
      "date": "timestamp",
      "modality": "write"
    }
  ]
}
```

**Word status flow:**
```
active    → in progress (any modality < 20)
archived  → mastered (all active modalities = 20)
```

**Synonym rule:**
Synonyms are only added to a word entry after `mastery.write.count >= 10`. Not before.

## Derived data (computed, not stored)

These values are calculated on the fly from stored data — do not store them as fields, calculate them when needed:

```
mistakes_per_task_this_month  → avg(submissions.mistake_count) for last 30 days
avg_word_count_this_month     → avg(submissions.word_count) for last 30 days
active_pool_size              → count(words where status = active)
archived_pool_size            → count(words where status = archived)
consecutive_days_missed       → today - user.streak.last_active_date
```

---

## Re-engagement logic (depends on Session + User)

```
consecutive_days_missed = 0-1  → no action
consecutive_days_missed = 2    → stage 1 notification
consecutive_days_missed = 4-5  → stage 2 notification (show word count)
consecutive_days_missed = 7    → stage 3 (show day 1 vs recent writing)
consecutive_days_missed = 14+  → stage 4 (soft re-onboarding, short task)
```

## Storage approach (open question)

| Option | Pros | Cons |
|--------|------|------|
| Local storage (v1) | No backend needed, fast to build | No cross-device sync, data loss risk |
| Supabase / Firebase | Real-time sync, auth included, free tier | More setup, dependency |
| Custom backend | Full control | Slowest to build |

**Recommendation for v1:** Start with local storage to validate the concept. Design all data structures as if they'll move to a real backend — use the same JSON shape. Migration later is straightforward if the shape is consistent from day one.
